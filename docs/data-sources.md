# Сравнение источников данных (открытая задача №1 и №2 из ТЗ)

Дата исследования: 2026-10-20/21, утренний час пик (~07:35–07:50 минского времени).
Метод: живые HTTP-запросы (curl), реверс JS-бандлов сайтов, два синхронных замера с интервалом 2 мин 45 с для проверки «живости» данных.

## Итог в одну строку

**Live-источник №1 — Яндекс Карты (прогноз вшит в HTML-страницу остановки, с разметкой live/расписание). Готового второго live-источника нет: Btrans — чистое расписание в JSON, Минсктранс — live GPS есть, но эндпоинт прогноза по остановке отвечает пусто. Роль «свежего расписания» отдаём Btrans JSON.**

## Важная поправка к ТЗ

Маршрут «114» фактически ходит как **114с** (скорый) — во всех источниках значится именно так. Настройки и парсеры должны ожидать «114с» (нечувствительно к регистру «с»).

## 1. Яндекс Карты (live-источник №1)

**Вывод: работает, данные отдаёт, капчи не было за ~20 запросов, куки и токены не нужны.**

Рабочий путь — не XHR-API, а сама страница остановки: прогноз прибытия вшит в HTML сервером.

- URL: `https://yandex.by/maps/157/minsk/stops/stop__<ID>/` (работает и `yandex.ru`, редиректит на `.by`)
- Метод: GET, заголовки — обычный User-Agent и `Accept-Language: ru`. Куки **не нужны** (проверено).
- Размер ответа ~355 КБ, время ~0,2 с.
- Прогноз лежит в блоке `<li class="masstransit-vehicle-snippet-view ...">`: номер, «до …», первая подача, следующие подачи, флаг `_live` (GPS) — если live-данных нет, показывается время по расписанию («19:31»).

Проверенный XHR-эндпоинт `yandex.ru/maps/api/masstransit/getStopPrediction` без полноценной сессии браузера отвечает эхом csrf-токена — возиться с ним смысла нет, страница надёжнее.

### Нужные stop-id (Малиновка)

| Блок ТЗ | Stop-id Яндекса | Что видно (проверено) |
|---|---|---|
| Блок 1: Малиновка-7 → метро/город | `stop__10044891` | 103 → ДС Юго-Запад, 114С → ДС Чижовка, 150 → Брилевичи; плюс 74С, 84, 1153ТК, 134С |
| Малиновка-7, встречное направление | `stop__10044924` | те же маршруты в сторону ДС Малиновка-4 |
| Блок 2: ст. метро Малиновка → Малиновка | `stop__10044918` | 103 → ДС Малиновка-4, 114С → Авторынок, 150 → Поворот к музею; плюс 96, 97, 10, 147, 25, 132 |
| Прочие платформы метро (для справки) | `10044950`, `10044974`, `10044897` | другие направления/маршруты |

У 150-го есть редкий пригородный вариант «до Поворота к музею» (Строчицы) — фильтровать маршруты по номеру, а не по назначанию. Точное соответствие платформ направлению (какая из платформ метро — «на Малиновку-7») стоит подтвердить на месте один раз.

### Риски

- Внутренний формат страницы без гарантий стабильности; вёрстка классов (`masstransit-prognoses-view__*`) может измениться — парсер за интерфейсом `ArrivalsSource`, сбой не роняет виджет (по ТЗ).
- Теоретический риск капчи при злоупотреблении частотой (не наблюдалось; наш паттерн — запрос по тапу/включению экрана с порогом свежести и 30-сек интервалом в мониторинге — консервативен).
- 355 КБ на запрос — терпимо для мобильного, но это самый «тяжёлый» источник.

## 2. Минсктранс, «Виртуальное табло» (кандидат на второй live)

**Вывод: сырой live есть (GPS машин), готового прогноза по остановке нет (204 No Content), доступ муторный (antiforgery + рандомизированный offset), стабильность низкая. Как второй live-источник в MVP не годится; остаётся запасным вариантом на будущее.**

Найдено (реверсом Angular-бандла): приложение по `https://minsktrans.by/lookout_yard/Home/Index/minsk`, API-база `POST /lookout_yard/Data/<Action>` (form-urlencoded), действия: `RouteList`, `Route`, `Track`, `Schedule`, `SchedulesByStop`, `TripDepartures`, `Vehicles`, `Scoreboard`, `StopNames`, `StopName`, `StopsByName`, `NearestStops`, `RouteSearch`.

Что нужно для запроса (проверено):

1. GET страницы `Home/Index/minsk` — забрать cookie `ASP.NET_SessionId`, cookie+поле `__RequestVerificationToken`;
2. в каждом POST передавать токен полем;
3. в `Scoreboard`/`Vehicles` ещё параметр `v = <id> + offset`, где offset генерируется **заново на каждую загрузку страницы** (наблюдались 54327, 52949, 11492) — берётся из `appSession` в HTML.

Результаты проверок:

- `Vehicles` (p=minsk, tt=bus, r=103): **200, JSON, 10 машин с GPS-координатами** — live-конвейер работает.
- `NearestStops`, `StopsByName`: 200, JSON (так найдены ID: Малиновка-7 = 58085 и 57886; ст.м. Малиновка = 57928 и др.).
- `Scoreboard` (p, s, v) — единственное, что даёт прогноз по остановке: стабильно **204 No Content** на все платформы, в т.ч. центральные, в час пик. Прогноза этим эндпоинтом сейчас нет.
- `SchedulesByStop`: 500 (не подобрал параметры).
- Стабильность: одни и те же запросы то 200, то 500 (токен/сессия протухают быстро, возможен rate-limit); поиск остановки с «не тем» написанием имени роняет сервер в 500. HTML-страницы сайта периодически отдавали 503.

Если когда-нибудь понадобится: прогноз можно собирать самостоятельно из `Vehicles` (GPS) + `Track` (геометрия) + `Schedule`, но это отдельный конёк сложности и для MVP не нужно.

## 3. Btrans.by (кандидат на второй live)

**Вывод: это НЕ live. Аккуратное плановое расписание, отдаётся простым JSON без защиты. Live-критерий провален, но источник отлично закрывает потребность в «свежем расписании».**

- Эндпоинт: `POST https://minsk.btrans.by/schedule-data` с телом `{}` и заголовком `Referer: https://minsk.btrans.by/ostanovka/<slug>` (контекст берётся из Referer). XHR не обязателен, работает без куки, ~0,15 с.
- Ответ: `{route, nearest, stopRoutes}`, где `nearest[<тип>][<маршрут>][<id платы>] = [[минуты_до_прибытия, графика_мин], …]` — ближайшие подачи уже посчитаны в минутах.
- Остановки: `/ostanovka/malinovka-7`, `/ostanovka/stancija-metro-malinovka`. Покрытие полное: 103, 114с, 150 на обеих.
- Доказательство «не live»: два замера с интервалом 2:45 — абсолютные времена (графиковые минуты) не изменились ни на секунду, сместились только «минуты до прибытия», ровно тикающие по часам. Это расписание, посчитанное на клиенте по HTML-табличке, только в JSON.
- reCAPTCHA на сайте подключена, но к `/schedule-data` не применяется.
- Минус для парсинга: по два идентификатора платформ на остановку (например 128962/029010 у Малиновки-7) без явной семантики направления — надо агрегировать обе.

## Сверка точности (замер 07:45 и 07:48, Малиновка-7, в сторону города)

| Маршрут | Яндекс 07:45 | Яндекс 07:48 | Btrans (расписание) 07:45 | Btrans 07:48 |
|---|---|---|---|---|
| 103 | 2 мин (live) | 7 мин (live) | 1 мин | 8 мин |
| 150 | 12 мин (расписание) | 11 мин (**live**) | 13 мин | 10 мин |
| 114с | 15 мин | 12 мин | 17 мин | 14 мин |

Расписание на этом коридоре ходит близко к факту (расхождение 0–3 мин), но живой дрейф есть: 150-й между замерами «стал» live-машиной и его следующая подача сдвинулась с 23 до 20 мин. Расписание не поймает опоздания и срывы рейсов.

## Сравнение по критериям ТЗ

| Критерий | Минсктранс (табло) | Btrans.by |
|---|---|---|
| JSON-эндпоинт или HTML | JSON, но за antiforgery-токеном и сессионным offset `v` | чистый JSON, без защиты |
| Покрытие обеих остановок, 103/114/150 | да (по `Vehicles`/поиску остановок); прогноз — нет | да, полностью |
| Это live? | GPS есть, прогноза нет (204) | нет, чистое расписание |
| Совпадение с Яндексом | не сравнить (нет прогноза) | ±0–3 мин (расписание) |
| Стабильность, капча | 200/500/503 вразнобой, токены протухают | стабильно 200 |
| Сложность парсинга | высокая (сессия, токен, offset, fallback-логика) | низкая (один JSON) |

## Решение (цепочка источников для MVP)

1. **Live: Яндекс** — страницы остановок `stop__10044891` и `stop__10044918`.
2. **«По расписанию»: Btrans `/schedule-data`** — вместо/поверх зашитого дампа: он уже в JSON, всегда свежий и с готовыми минутами. (Зашитый дамп в Room остаётся последним рубежом на случай недоступности сети — наполняется из этого же JSON.)
3. **Кэш Room** — между ними, как в ТЗ.
4. Минсктранс — в резерв: следить, не «оживёт» ли `Scoreboard` (раз в квартал); `Vehicles` уже сейчас пригодился бы для карты машин, если захочется.

Таким образом, «второго live-источника» в MVP не будет — его место занимает более честный фолбэк на свежее расписание. Это покрывает главный сценарий отказа (Яндекс отдал капчу/смену вёрстки) без ложных «живых» цифр.
