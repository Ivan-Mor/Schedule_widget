# Принятые решения (дополняют ТЗ v2)

Дата: 2026-10-20.

## Мониторинг «Выхожу»

- Следим за **всеми выбранными маршрутами**; каждый маршрут присылает **одно уведомление на рейс** (первый рейс, попавший в настраиваемый порог «пора», например ≤ 5 мин).
- Мониторинг останавливается: по таймеру (план — 15 минут) **или** когда каждый отслеживаемый маршрут прислал своё уведомление. Одно сработавшее уведомление не глушит остальные маршруты.
- Мониторинг следит только за **одним направлением**, выбранным в настройках (например, утром «Малиновка 7 → метро», вечером переключить на обратное).

## Расписание (последний фолбэк)

- Плановое расписание маршрутов 103/114/150 на обеих остановках **зашивается в APK** (prepopulated Room). Обновление — вместе с обновлением приложения. В Settings API/парсеры выгрузок Минсктранса в MVP не тащим.

## Виджет 4×2

- Раскладка — **две колонки**: слева «Малиновка 7 → метро», справа «Ст. метро Малиновка → Малиновка 7»; общий футер (время последнего обновления, статус данных, кнопки «обновить» и «Выхожу»). Переключатель направлений не делаем.
- Дефолтные параметры (уточняются в настройках): порог свежести данных — 45 с; порог «пора» — 5 мин; длительность мониторинга — 15 мин; интервал опроса в мониторинге — 30 с.
- Тема: тёмная 18:00–06:00, светлая 06:00–18:00. Тема применяется при каждой перерисовке; в 18:00/06:00 планируем дешёвую перерисовку без сети (AlarmManager), чтобы тема не «залипала».
- Режим «по расписанию» показывает точное время ближайшего рейса (например, «18:43»), а не минуты. Если рейсов нет вовсе (ночь) — строка «нет рейсов».

## Технические следствия

- Обновление при включении экрана: receiver на `ACTION_USER_PRESENT` + перерисовка с проверкой порога свежести (без сети, если данные свежие). После перезагрузки телефона ресивер переподключается через `BOOT_COMPLETED` (разрешение `RECEIVE_BOOT_COMPLETED`).
- minSdk = 36 (единственное устройство — Redmi 14S, Android 16). Язык UI — русский.
- У Яндекса нет публичного API прогноза прибытия — источник №1 проверяется исследованием внутренних эндпоинтов. Если Яндекс окажется нестабильным (капча, токены), порядок live-источников пересматриваем по результату сравнения (см. открытое сравнение Минсктранс vs Btrans.by).

## Источники данных (по итогам исследования 2026-10-20, детали — data-sources.md)

- Live-источник №1: **Яндекс Карты** — GET страницы остановки (`stop__10044891` — Малиновка-7 → город; `stop__10044918` — метро → Малиновка), прогноз вшит в HTML, есть флаг live/расписание. Куки не нужны.
- Роль «свежего расписания»: **Btrans `POST /schedule-data`** (JSON, обе остановки, 103/114с/150). Это НЕ live — доказано замерами.
- Зашитый дамп в Room наполняется из того же JSON Btrans и остаётся последним рубежом офлайна.
- Минсктранс (табло `/lookout_yard/Data/*`): live GPS машин работает, но прогноз по остановке (Scoreboard) стабильно пуст (204), доступ за antiforgery + сессионным offset. В MVP не используется; проверять раз в квартал.
- Маршрут «114» фактически ходит как **114с** — парсеры и настройки это учитывают.

## Открытые вопросы

- Финальные значения порогов (свежесть 30–60 с, «пора», длительность и интервал мониторинга) — подтвердить при разработке экрана настроек.
- Подтвердить на месте соответствие платформ направлениям (какая платформа метро — строго «на Малиновку-7»).
